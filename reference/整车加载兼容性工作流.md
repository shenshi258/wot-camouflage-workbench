# 整车加载兼容性工作流

适用于本项目制作和修改的涂装、模型、材质、着色器、动画、光效及 `.wotmod`。整车加载兼容性是固定验收项，记录采用 [验证记录模板](整车加载验证记录模板.json)。本流程是必须执行的操作与记录要求；现有文件校验按钮不会自动完成游戏内测试。

## 1. 建立实际环境和原版基线

1. 从本次启动日志、已安装包或快捷方式确认实际客户端绝对路径、区服和版本，同时读取其 `paths.xml`。不能只引用工作台的默认设置。
2. 记录原始包与待测包的文件名、大小和 SHA256，保留原始文件。
3. 确认同一客户端、同一车型和配置下，未改动的原始包能否正常加载。区分用户确认与代理亲自观察；基线不明时先取得基线，不能把原包天然正常当作事实。
4. 检查 `mods` 和 `res_mods` 的相关覆盖、同款重复包、大小写不同的同名资源及相关着色器覆盖。不要为排查本涂装随意移除其他模组或删除整个缓存。
5. 测试前记录日志起始位置。后续只分析本次测试区间；截图中的通用崩溃对话框不构成根因证据。

## 2. 文件与依赖校验

- 检查 ZIP CRC、无压缩格式、重复条目、相对路径、完整资源清单和修改范围。
- 沿 `.model → .visual_processed → .primitives_processed → 材质/贴图/着色器` 检查依赖，并以实际客户端及实际覆盖顺序解析。
- 同时检查底盘、车体、炮塔、炮管的节点、父子关系、骨骼与蒙皮、primitive groups、顶点格式、材质标识和 LOD 关联；单部件回读通过只覆盖该部件。
- 更换材质或着色器时核对原生 Compound 路径支持、参数名称和类型、运行时绑定、顶点声明、蒙皮要求、混合和透明状态及渲染分支。着色器编译通过、文件存在、材质接口相同均不足以确认整车兼容。
- 检查各贴图的格式、尺寸、mip 和引用，避免把历史缺纹理警告直接认定为本次闪退原因。

该阶段通过只标记 `file_validation.status = passed`。

## 3. 部件回读与离屏渲染

- 对实际最终包中的资源验证，避免只测试重新生成的一份中间资源。
- 按修改内容检查网格回读、着色器实际执行、亮度曲线、颜色、透明度、混合状态和必要的渲染分支。
- 着色器枚举必须从当前客户端的元数据或原生定义核实。离屏测试必须核对最终材质实际选择的模式，不能跳过模式选择、手工挑选一个能产生目标效果的分支后宣布通过。
- 检查每个车体及附加模型的全部 primitiveGroup 引用与索引缓冲分组数、顶点范围；不能只检查新提取的灯面。原包中已有的缺陷也要单独记录。
- 记录工具、范围、结果及与原始资源的对照。无法适用的离屏检查填写说明，不能用它代替游戏验证。
- 脚本加载、序列绑定成功仅证明执行到了绑定阶段，不能替代实际可见效果验收。尤其不能据此断定 Compound 上的材质参数可被动态控制。独立模型方案还须检查序列、模型、visual、顶点格式、贴图、挂点与清理链。

该阶段结果单独记录为 `offline_validation`，不得自动更新整车状态。

## 4. 游戏内整车加载验收

在实际客户端中启用唯一待测版本，复核启用包的 SHA256。按顺序检查：

1. **首次加载车库整车**：确认四个部件成功合成，车辆加载完成，无 Compound 构建失败、资源错误引发的异常或闪退。
2. **重复加载**：切换到其他车型再切回，重新进入车库或重启后复测，排除只在首次或缓存命中时正常的情况。
3. **姿态与状态**：转炮塔、俯仰炮管、观察履带与悬挂；检查透明边缘、发光遮挡和材质一致性。
   独立特效还须检查开镜、退镜、场景隐藏及恢复。开镜可能仅保留阴影绘制位，不能把非零 visible 标志当作车体可见。轮边灯的校正变换应放在特效自己的节点，避免改动原车履带/车轮共享挂点。
4. **距离与 LOD**：在训练房或适用的本地回放中检查远近切换，确认修改涉及的各级 LOD 和皮肤变体；未覆盖的范围明确登记。
5. **光效连续运行**：至少观察多个完整循环，检查不同视角及适用画质分支，确认没有逐帧资源错误、异常闪烁或加载后延迟崩溃。
6. **日志复核**：对照本次起止时间或行号，保留相关加载完成、错误和异常证据。没有某条错误并不单独证明测试成功，必须同时有实际整车加载观察。

记录观察者、客户端、区服、版本、车型配置、画质、测试时间、最终包哈希及每个场景的结果。只完成部分场景时，完整验收状态仍保持 `not_tested` 并注明已完成的范围。

## 5. 状态和交付规则

| 状态 | 使用条件 | 对外说明 |
| --- | --- | --- |
| `not_tested` | 未实测、仅离线验证，或整车验收尚未完成 | 待游戏内整车复测；不得声称兼容通过 |
| `passed` | 最终包在所记录实际环境中完成上述适用验收，有对应观察和证据 | 仅说明已验证的版本、配置和范围 |
| `failed` | 任何适用场景发生整车加载失败、相关异常或闪退 | 停用该版本，保存证据并回到正常基线 |

`in_game_tested` 只表示是否尝试过游戏测试，不能独立表示通过；`complete` 只表示构建完成。整车通过必须读取 `whole_vehicle_loading.status`。不能将多个阶段合并成含糊的“校验通过”。

包内容、哈希、客户端版本、画质分支或相关覆盖关系改变后，先前通过结论不再自动适用。新构建默认从 `not_tested` 开始；已失败包不能因离线重测通过而恢复为可用。

无法在当前环境完成实测时，保存待复测产物并准确报告限制，不增加无依据的确认流程。需要用户参与时说明具体测试场景和待确认结果，不要求用户反复尝试没有新证据支撑的“修复版”。

## 6. 闪退处置和本项目案例

1. 记录最终包哈希及本次日志，立即将对应整车状态改为 `failed`，撤回可用或已修复的结论。
2. 优先恢复或指导恢复已知正常的原始涂装，保留失败包及修改记录用于诊断。没有执行回滚时不能声称已恢复。
3. 分开记录已确认的错误、推测原因和后续验证办法。对旧警告和其他模组报错先做安装前后对照。
4. 从正常基线一次改变一个因素，验证后再扩大修改范围；同一报错再次出现时回查假设，不重复用离屏结果代替整车证据。
5. 摘录日志时去掉登录令牌、会话及账号凭据。崩溃报告上传需用户明确要求。

SFAC105 案例（2026-10-23）：用户确认原始「【BA】铁道双子SFAC105.wotmod」在欧服可正常加载；呼吸灯初版在 12:40:42、12:45:00 发生底盘 `Compound building failed`，兼容修正版在 12:59:04 仍发生相同错误，随后异常码 `0xC0000005`，调用栈哈希相同。后者通过了离屏渲染，但整车验收失败。修改着色器路径或材质接口导致兼容问题属于待验证假设，不能写成已证明的内部根因。两个呼吸灯版本均应登记为 `failed`。

后续直接控制原有材质的原生序列测试包（SHA256 `ad4728a49e022ef3b65e52f8b8b4177191b5a7d0e47e03b8030b3555ec874e90`）在 13:36:16 记录四部件绑定，但用户报告灯光不变化，功能验收失败。绑定日志不能恢复其通过状态。用户随后明确要求按蜘蛛方式使用独立特效模型，并要求游戏内实测由用户自行完成；新包的整车状态保持 `not_tested`，直至对应最终哈希的实际测试结果返回。

蜘蛛独立特效 R1（SHA256 `412df7893318575ca1908c6868e7a33fdcca236f41eda2e7dbbb28c3ce4c9ab6`）随后被用户实测判定失败：车库与战斗中没有呼吸循环、履带消失，开镜有附加模型遮挡。已确认模式枚举填错（Pattern=1、Pulse=2），旧离屏检查漏检模式选择；同时漏测开镜绘制位传播。履带消失的具体根因仍待确认。原包既有的炮管不存在网格分组引用须单独记录，不得直接归因为此次新增故障。R2 保留单独构建和验证记录，交付时未由代理安装；用户随后反馈“完成了”。此反馈作为用户完成反馈记录，不自动补写未逐项记录的场景通过状态。

## 7. 呼吸灯专项工作流

制作独立呼吸灯时，执行 [呼吸灯制作工作流](呼吸灯制作工作流.md)。该工作流固化了本次的制作路径、参数来源、生命周期、开镜绘制位同步、自有节点隔离和故障对照规则。

- 参数验收须覆盖最终材质的实际模式选择和对应渲染分支。
- 灯面从原车提取后必须校验局部坐标、UV、权重及随动；特殊锥顶校正不能推广到任意蒙皮网格。
- 挂载与变形由特效自己的模型节点承载，保留原车共享节点和履带状态。
- 开镜隐藏、退镜恢复和切车清理都是必测项。
- 原包已有问题单独记录；全部车体和特效网格都检查分组范围。
- 复用工程先建立新修订和独立输出，保留旧包、哈希和失败记录。

蜘蛛独立特效 R2（SHA256 `650c5de9274348767fd9cffc34d59103b2ce6072a8691fbf67d75ac1a8186bb7`）在用户实测中暴露功能缺陷：炮管上的灯效不随炮管俯仰变化，未报告闪退。定位依据客户端字节码：TankNodeNames.GUN_INCLINATION == "Gun" 才是被 appearance.gunMatrix 驱动的倾角节点，"gun" 只是 ModelAssembler.addPart 建立的部件别名；R2 把炮管灯挂在别名上，所以只随炮塔和车体。R3（SHA256 `a0c89e72b080b30042d9f13cef97ec5cba3c06b8be43ab4e8367ee70f416d3fe`）只改这两处挂点，灯面顶点与材质不变，整车状态仍为 `not_tested`，待用户实测。

R3（SHA256 `a0c89e72b080b30042d9f13cef97ec5cba3c06b8be43ab4e8367ee70f416d3fe`）由用户实测确认炮管灯随俯仰生效，按用户确认记录为通过（只覆盖该反馈；开镜、LOD、多循环、切车未逐项书面确认）。随后用户要求整体提亮：原生着色器实测显示交付分支把 g_forwardMult/g_deferredMult 编译掉了，g_zeroPhaseLum/g_contrast 也无效果，唯一线性可控的亮度参数是 g_tint。R4（SHA256 `a9103cdc2cbaebe11d7362962d7a558dbc3bb20afb0837047e3b2b62d32abb3c`）只把 g_tint 由 1 提到 1.5，实测峰值 1.4→2.1、逐像素比 1.5，呼吸曲线与 alpha 不变，整车状态从 `not_tested` 重新开始。

星野 P65 光环光效 R2（SHA256 `d4bbf8e32324716470bc7aa4d895093bb7ad3e97fa67946f7c7118b40bbaa7fc`）由用户实测看到光环，随后要求提亮并降低透明度。原生 glow.fx 离线实测确认：纯叠加混合（src 3 / dest 2）下背景 100% 透出，等效不透明度为 0；材料参数里 `selfIllumination` 与 `destBlend` 才是亮度与“透明度”的把手，与 SFAC105 呼吸灯用的 emissive_playground 完全不同，不能把两套材质的参数含义混用。R3（SHA256 `bab2a1d5cc0b5f94361f4e67f3f3594c0b41e57a890b8b9b541903cbc042300f`）只改 `selfIllumination` 0.6→1.6、`destBlend` 2→6、光环贴图 alpha 255→230，实测亮度 2.43×（分支 10）/1.44×（分支 11）、等效不透明度 0→0.902，整车状态重新从 `not_tested` 开始。

水星野 Pz70 侧面流星 R1（SHA256 `dabed3691f5dc3b42b2c80e77fc17d8044364953cd9362fc0027d8cf256b1a8b`）在欧服 2.4.1.1 的用户录像中可见移动，但用户报告光头约为预览三倍、尾部形状不一致，视觉验收失败，登记为 `failed`；未报告闪退，不得写成 Compound 构建失败。读取当前客户端 emissive_playground 枚举确认 srcBlend=3 为 SRCCOLOR，5 才是 SRCALPHA。R1 预览按 alpha 加法，而包用 3/6，旧 GPU 检查只看混合前像素输出，漏检实际混合。对最终纹理执行原生像素程序与真实 D3D 混合，复现了 R1 的大面积实色光头和硬尾；这证明了混合不一致，未证明它是游戏差异的唯一原因。R2（SHA256 `d3150d416cb5c807f86728e23e8c88f944a2888bd93c6313cae729924b6b2478`）仅将两个附加材质的 srcBlend 3→5、destBlend 6→2；几何、纹理、序列、亮度和原车资源逐字节不变，四个相关像素分支真实混合检查完成。状态保持 `not_tested`，需最终包的实际效果复测。软边特效以后必须验证混合后 RGB/alpha 及背景，并让预览使用最终材质的同一公式，不能将混合前 alpha 正确当作软边正确。
